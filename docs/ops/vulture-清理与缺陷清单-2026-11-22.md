## 二、真实缺陷（3 条，建议改，但会动到行为，所以先不动）

### 1. `worker_helpers._bump_parent_score`：说好要写说明，从来没写

```python
def _bump_parent_score(conn, parent_id, child_score, child_reasoning) -> bool:
    """
    If the child's score is more extreme than the parent's, update the
    parent's sentiment_score **and prepend a note to the reasoning field**.
    """
    ...
    if abs(child_score) > abs(parent_score) and (child_score * parent_score >= 0):
        conn.execute(
            "UPDATE ai_decisions SET sentiment_score = ? WHERE id = ?",
            (round(child_score, 4), parent_id),
        )
        return True
```

docstring 承诺了两件事，实现只做了一件。`child_reasoning` 在整个函数体里出现 0 次
（AST 计数确认），`reasoning` 字段没有任何 UPDATE。

影响：子决策把父决策的分数往极端方向拽时，父决策的 `reasoning` 里看不到"为什么被改分"。
事后复盘 `ai_decisions.reasoning` 会缺一块因果链——而这块正是这个项目对外讲的核心：
**决策要留痕、要能解释**。

修法（两行，但要确认文案口径）：在 UPDATE 里一并写 `reasoning = '【子决策提分】' || ? || ' | ' || COALESCE(reasoning,'')`。
风险：会改变已有决策的 reasoning 文本格式，前端解析如果按 `|` 切分会受影响。所以需要你确认。

### 2. `judge_worker`：清洗代码被 `return` 挡在后面

```python
     except Exception as e:
         print(f"[JUDGE] JSON parse FAIL ({source}): {e}", flush=True)
         return None
         # 2) 剥 markdown ```json 包裹          ← 永远不会执行
         if text.startswith("```"):
             ...
```

顺序错了：先解析、失败就 return，后面"剥 ```json 包裹再解析"的补救逻辑是死的。

影响：模型返回带 ```json 包裹的内容时，本可以被清洗后解析成功，现在直接判失败。
即 **LLM 输出的 markdown 包裹会导致判官静默丢结果**，且只在日志里留一行 parse FAIL。

这条比第 1 条的杀伤面更大，因为它影响的是"解析成功率"。建议把 227 行之后的清洗块
整体上移到 `return None` 之前。改完要跑一遍 `tests/test_ai_worker_review.py` 一类用例。

### 3. `_rescue_target_asset_from_content`：分类偏好传了但没生效

`ai_worker.py` 与 `worker_helpers.py` 各有一份同名实现，参数 `preferred_categories`
在 AST 里计数为 0，但 docstring 明确写了"优先分类"。

影响：LLM 把 `target_asset` 写成 NONE/OTHER 时，服务端兜底从正文猜 ticker，
本该按分类偏好加权，实际完全没加权 → 兜底可能猜到非偏好品类。
（顺带一个结构问题：两份同名实现本身就该合并成一份，属于后续拆分任务。）
