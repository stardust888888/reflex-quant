# 质量门禁接入说明（2026-11-22）

## 为什么接，接之前它长什么样

三轮拆分（`prompt_blocks` / `insights_store` / `attribution_store`）是靠**人记得不许反向 import** 守住的。
人记不住。接 `import-linter` 的第一次运行就抓到一个真实问题：

```
engine.prompt_blocks → review.review_agent → engine.ai_worker → engine.worker_helpers
```

`prompt_blocks` 第 551 行延迟 import 了 `review.review_agent`——但 `review_agent` 只是把
`build_active_insights_section` / `seed_analysis_experience` 从 `insights_store` **re-export** 出来。
绕这一圈的结果：刚拆开的两块，通过一条间接路径又连回去了。

改成直接 `from review.insights_store import ...` 后，依赖链断开，三条契约全绿。
这不是"为了让检查通过而改配置"，是检查抓出了拆分没拆干净的地方。

## 四个检查各管什么，不管什么

| 检查 | 管 | 不管 |
|---|---|---|
| import-linter | 模块间依赖方向、成环 | 业务逻辑 |
| vulture | 无人使用的变量/函数、不可达代码 | 动态调用（`getattr`、插件注册） |
| deptry | 依赖声明与实际 import 是否一致 | 版本是否安全 |
| complexipy | 认知复杂度 | 写得对不对 |

**四项都不检查业务逻辑正确性。** 闸门拦得准不准，只有 `scripts/gate_baseline.py` 的反事实回放
和真实样本能回答。把这两类结论混为一谈，是这个项目最容易犯的错。

## 基线冻结：为什么不直接全量报错

首次接入的存量：

| 项 | 存量 | 处理 |
|---|---|---|
| vulture（`--min-confidence 100`） | 26 条 | 冻结在 `.quality/vulture_baseline.txt` |
| complexipy 认知复杂度 > 25 | 548 个函数 | 冻结在 `.quality/complexipy_baseline.json` |
| 最高复杂度 | `ai_worker()` = **1978**，`_call_llm_sync` = 1158 | 只记录，不动 |
| deptry DEP002 | `pandas` / `ccxt` / `streamlit` | 冻结，注明待清理 |

直接全量红，人的第一反应是加 `--ignore`，门禁当场作废。所以 `quality_gate.py` 只回答：

- vulture：**有没有新增**（修掉的会提示基线该变短）
- complexipy：新增函数 > 25 分 → 红；老函数涨超过 +3 → 红
- import-linter / deptry：契约与配置本身就是红线，直接执行

## 验证过它真的会红

不是只跑通就交差。在 `insights_store.py` 尾部临时注入一个死变量，单独跑 vulture：

```
vulture : 当前 27 条，基线 26 条 → 新增 1 条 ❌
  + src_python/review/insights_store.py :: unused variable '_dead_probe'
```

还原后回到 26 条、绿。**门禁能抓到新增，这是它唯一有用的性质。**

## 本地怎么跑

```bash
cd backend
pip install -r requirements-dev.txt     # 只装工具，不装运行依赖
python3 scripts/quality_gate.py         # 全跑，有退化退出码 1
python3 scripts/quality_gate.py --only vulture
python3 scripts/quality_gate.py --update   # 修完代码后手动重冻基线
```

CI：`.github/workflows/quality.yml`，`backend/**` 变更时触发，约 20 秒（不装 fastapi/ccxt，
四个检查全靠 AST 与依赖清单）。表格同时写进 Job Summary。
